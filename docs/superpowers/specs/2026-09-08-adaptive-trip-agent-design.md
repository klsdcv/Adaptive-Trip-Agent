# Adaptive Trip Agent 설계
작성일: 2026-09-08
상태: 대화에서 승인된 설계를 문서화함. 문서 검토 후 구현 계획 작성.

## 1. 목표와 문제 정의

국내외 여행자가 날씨·교통·휴무·일정 지연 등 상황 변화에도 여행을 이어갈 수 있도록, 현재 상태와 사용자 조건을 바탕으로 실행 가능한 대안을 먼저 제안한다.

여행자는 장소, 날씨, 영업시간, 이동시간 등 분산된 정보를 조합해야 한다. 여행 중 변화가 발생하면 남은 일정을 다시 검토하고 조정해야 한다. 이 반복적인 정보 확인과 의사결정 부담을 줄이는 것이 제품의 목표다.

검증할 가설: 외부 정보를 조회하고 여행 상태를 유지하며 제약 검증과 재계획을 반복하는 Agent는 한 번의 일정 생성·수정보다 제약 충족과 변화 대응에 유리하다. 이를 평가로 확인하며, 아직 입증된 효과로 주장하지 않는다.

기존 대화에 인용된 여행 관련 설문 수치는 원문 미확인 상태이므로 근거로 채택하지 않는다.

## 2. 사용자와 범위

- 대상은 국내외 여행자 전체다. 특정 국가나 도시로 입력을 제한하지 않는다.
- 초기 실제 연동 검증에는 사용자가 경험한 오사카·후쿠오카를 활용한다. 국내 사례도 포함해 지역별 정보 부족 처리를 확인한다.
- 지역별 정보 지원 차이는 도구 결과의 지원 여부·정보 부족 상태로 표현한다. 전 세계에서 동일한 데이터 품질을 보장한다고 표시하지 않는다.
- 사전 일정 생성 약 30%, 여행 중 상태 변화와 재계획 약 70%에 개발·시연의 비중을 둔다.
- 여러 날짜의 일정을 관리하되, 초기 재계획은 해당 날짜의 남은 현지 일정을 수정한다. 날짜를 넘기는 변경은 자동 확정하지 않는다.
- 초기 경로 검증은 도보·대중교통을 중심으로 한다. 다른 이동수단은 지원 여부를 명시하고, 미지원 경로를 검증 완료로 표시하지 않는다.
- 항공권·숙소 구매, 예약 변경·취소 실행, 결제 내역 자동 수집은 초기 구현 범위에 포함하지 않는다. 사용자가 입력한 예약은 고정 조건으로 관리한다.
- 혼자 개발하는 포트폴리오이며 기간보다 아래의 완성 기준을 우선한다.

## 3. 완성 기준

1. 기존 일정 입력과 새 일정 생성이 모두 가능하다.
2. 현재 시간·위치, 완료 일정, 입력된 지출, 취향과 사용자 선택을 유지한다.
3. 여행 모드에서 날씨를 주기적으로 조회하고 일정 영향이 있을 때 먼저 대안을 제안한다.
4. 사용자가 입력한 지연·현장 휴무·피로·선호 변경을 재계획에 반영한다.
5. 기본 3개의 구별되는 대안을 제안하고 변경 이유와 영향을 설명한다.
6. 고정 조건과 계산 가능한 제약을 검증하며 충돌을 숨기지 않는다.
7. 선택된 제안만 확정하고 거절·추가 요청에 따라 다시 제안한다.
8. API 오류, 정보 부족, 대안 부재를 처리하며 반복 호출을 제한한다.
9. 재현 가능한 시나리오로 제약 충족, 대응 성공, 상태 일관성, 시간과 비용을 평가한다.

## 4. 입력과 조건

기존 일정은 자유로운 텍스트를 구조화된 일정표로 변환한 뒤 사용자가 확인한다. 모호한 장소는 후보로 확인하고, 누락된 시간이나 체류시간을 추정하면 추정임을 표시한다. 검증에 필요한 정보가 없으면 추가 입력을 요청한다.

새 일정 생성은 여행지·날짜·시작 및 종료 조건·취향을 받아 도구 조회와 검증을 거친 초안을 제시한다. 사용자가 확인한 초안이 확정 일정이 된다.

조건은 다음과 같이 구분한다.

| 종류 | 예시 | 처리 |
|---|---|---|
| 고정 조건 | 예약 시간, 필수 방문, 최종 도착 시간 | 사용자 동의 없이 변경하지 않음 |
| 조정 가능한 선호 | 활동 종류, 걷는 양, 순서 | 후보 비교에 사용 |
| 예산 | 절대 상한 또는 선호 금액 | 사용자가 강도를 지정 |
| 환경 정보 | 날씨, 영업시간, 경로 | 조회 시각과 출처·확인 상태 보존 |

가격 수준을 정확한 결제액으로 취급하지 않는다. 비용은 확인된 지출과 예상 비용을 구분하고 통화를 보존한다. 서로 다른 통화를 환산 근거 없이 합산하지 않는다. 비용 누락으로 예산을 검증할 수 없으면 미확인으로 표시한다.

## 5. 구성 요소와 책임

| 구성 요소 | 입력 | 출력·책임 |
|---|---|---|
| 일정 입력·생성 | 사용자 텍스트 또는 여행 조건 | 확인 가능한 일정 초안 |
| 여행 상태 관리 | 확정 일정, 상태 이벤트, 사용자 선택 | 버전이 있는 현재 여행 상태 |
| 상황 확인 | 활성 여행, 날씨 조회, 사용자 이벤트 | 중복을 제거한 변화 이벤트 |
| 재계획 Agent | 상태, 변화, 고정 조건 | 필요한 도구 선택과 대안 후보 |
| 도구 어댑터 | 장소·경로·날씨 조회 요청 | 출처·시각·오류 상태를 갖는 정규화 결과 |
| 제약 검증 | 후보 일정, 상태, 도구 결과 | 통과·위반·미확인 및 이유 |
| 제안·선택 처리 | 검증 결과, 사용자 선택 | 제안 표시 또는 확정 상태 갱신 |
| 평가·실행 기록 | 실행 단계와 검증 결과 | 지표, 호출량, 비용 추정, 실패 원인 |

처리 흐름·상태 변경·시간과 비용 계산·반복 제한은 코드가 맡는다. LLM은 요청 해석, 정보 필요성 판단, 도구 선택, 대안 구성과 설명을 맡는다. LLM의 설명을 검증 결과 대신 사용하지 않는다.

기술 스택 선정은 구현 계획 단계에서 이 책임과 계약에 맞춰 진행한다. 초기 배포 구조는 하나의 애플리케이션 안에서 위 역할을 모듈로 분리하는 것을 기본으로 한다.

## 6. 상태 모델

- Trip: 여행 기간, 목적지, 시간대, 사용자 조건, 여행 모드 여부.
- ItineraryItem: 장소 식별자·좌표, 시작·종료 시각, 체류시간, 상태, 예약·고정 여부, 비용과 확인 상태.
- TripState: 현재 위치와 갱신 시각, 현재 시각, 완료·진행·남은 일정, 지출, 일정 버전.
- Observation: 출처, 조회 시각, 적용 시간, 장소·날씨·경로 정보, 성공·미지원·정보 부족·실패 상태.
- ChangeEvent: 발생 시각, 원인, 영향받는 일정, 처리 상태와 중복 식별 정보.
- Proposal: 기준 일정 버전, 변화 이벤트, 후보 일정, 변경 목록, 검증 결과, 작성 시각, 제안 상태.
- Decision: 제안 선택·거절·추가 요청과 선택 시각.
- ExecutionRecord: 실행 식별자, 도구 요청·결과 상태, 검증 결과, 호출 횟수와 지연시간·비용 추정.

확정된 사실, 조회 정보, 미확정 제안은 분리한다. 위치·지출은 사용자 입력을 기본으로 하고 브라우저 위치는 사용자가 허용한 경우 활용한다. 시각은 시간대가 있는 값으로 관리하고 화면은 해당 여행지의 현지 시각을 표시한다.

재계획이 진행되는 동안 확정 일정을 수정하지 않는다. 선택 반영은 기준 버전을 확인한 뒤 원자적으로 수행하며, 동일한 선택 요청을 반복해도 한 번만 반영한다.

## 7. 재계획 흐름

1. 변화 이벤트와 현재 상태를 확보한다.
2. 남은 일정에 실제 영향이 있는지 판단한다. 비 예보만으로 모든 야외 일정을 불가능하다고 판단하지 않는다.
3. 완료 일정과 고정 조건을 보존하고 수정 대상 구간을 정한다.
4. 필요한 장소·경로·날씨를 조회한다.
5. 대안 후보를 구성한다.
6. 이동시간, 체류시간, 도착·종료 시각, 영업시간, 고정 조건, 예산을 검증한다.
7. 위반이 있으면 설정된 호출·반복 한도 안에서 추가 조회하거나 수정한다.
8. 구별되는 유효 대안 3개를 목표로 제안한다.
9. 사용자 선택 시 일정 버전과 시간 경과로 영향을 받는 제약을 재확인한다.
10. 문제가 없으면 확정하고 변경 내역을 표시한다. 오래된 제안이면 다시 계산한 뒤 사용자에게 확인한다.

대안은 단순한 문구 차이가 아니라 장소·동선·비용·활동 성격 등 의미 있는 차이를 가진다. 차이를 만들기 위해 고정 조건을 어기지 않는다.

통과한 후보가 3개 미만이면 가능한 수만 제시하고 이유를 설명한다. 미확인 항목이 있는 후보는 확인이 필요한 선택지로 구분하고 실행 가능하다고 단정하지 않는다. 0개라면 조건 충돌과 완화할 수 있는 선택지를 제시하며, 조건 완화는 사용자 동의 후 수행한다.

## 8. 화면 흐름

### 시작과 일정 확인

새 일정 만들기 또는 기존 일정 가져오기 → 텍스트·조건 입력 → 장소·시간 확인 → 고정 조건 지정 → 일정 확정.

### 여행 중 메인 화면

| 영역 | 내용 |
|---|---|
| 오늘의 일정 | 완료·진행·남은 일정, 고정 조건, 예상 이동시간 |
| 상황 알림과 대안 | 영향 원인, 기본 3개 후보, 변경 비교, 검증·미확인 결과 |
| 대화·상태 입력 | 지연, 현장 휴무, 피로, 취향 변경, 방문 완료 입력 |

대안 카드에는 변경 장소, 변경 이유, 예상 이동량, 비용과 통화, 고정 조건 충족 여부, 미확인 정보를 표시한다. 사용자는 선택, 기존 일정 유지, 다른 대안 요청을 할 수 있다.

선택 전에는 원본과 후보를 비교하고, 반영 후에는 변경된 항목을 표시한다. 거절하면 기존 일정을 유지한다. 조건 충돌이 있으면 변경해야 할 조건과 결과를 설명한다.

### 먼저 제안하기

여행 모드 활성 시간에 서버가 날씨를 주기적으로 확인한다. 조회 주기와 호출 한도는 설정으로 관리한다. 일정에 의미 있는 영향이 있을 때 연결된 화면에 알림을 전달한다. 같은 상황의 알림은 중복 억제하고, 이미 거절한 제안은 관련 상황이 실질적으로 변하기 전 반복하지 않는다.

모바일 푸시는 후속 확장이다. 화면 재접속 시 현재 상태와 남아 있는 제안을 다시 조회한다. 현장 휴무·실제 지연 등 조회로 알 수 없는 상황은 사용자 입력으로 받는다.

## 9. 외부 정보와 비용 관리

Google Places·Routes·Weather를 첫 연동 후보로 사용하되, 지역·이동수단별 실제 응답을 확인한다. 도구 어댑터는 미지원과 정보 부족을 명시적으로 반환한다. 특정 제공자에 맞춘 응답 형식을 Agent 상태에 직접 종속시키지 않는다.

월 무료 사용량 안의 개발·시연을 목표로 한다. 무료량을 무제한 사용으로 취급하지 않는다. 요청 필드·기능 등급과 과금 단위를 반영해 사용량을 기록하고, 실행당 호출·반복 제한 및 애플리케이션 측 사용량 차단을 둔다. 공급자 쿼터도 가능한 범위에서 설정하며 예산 알림만으로 자동 차단된다고 가정하지 않는다.

실제 API는 연동 검증·시연에 사용하고 반복 테스트는 직접 작성한 합성 데이터로 수행한다. 외부 데이터의 저장·재사용 범위는 제공자 정책 확인 후 구현한다. LLM 사용료는 지도·날씨 API와 별도로 기록한다.

## 10. 실패 복구

| 상황 | 동작 |
|---|---|
| 일시적 API 실패 | 제한된 재시도 후 확인 불가 표시 |
| 미지원 경로·지역 | 미지원 명시, 검증 통과로 간주하지 않음 |
| 영업시간·비용 누락 | 미확인 표시, 필요하면 사용자 확인 |
| 만족 가능한 대안 없음 | 충돌 원인과 조건 완화 선택지 제시 |
| 호출·비용 한도 도달 | 추가 조회 중단, 확인된 결과와 한계 안내 |
| 구조화되지 않은 LLM 출력 | 형식 검증 후 제한된 재시도, 실패 시 기존 일정 유지 |
| 오래된 제안 선택 | 최신 상태에서 재검증, 달라진 내용 다시 확인 |
| 중복 이벤트·선택 | 중복 억제, 상태 한 번만 갱신 |

외부 장소 설명이나 도구 응답은 정보로 취급하고 시스템 동작을 바꾸는 지시로 실행하지 않는다. API 키는 서버에서 관리하며 로그에 남기지 않는다.

## 11. 평가 설계

### 비교 대상

A. LLM이 한 번에 일정을 생성·수정하는 방식.
B. 동일한 초기 외부 정보를 제공하고 한 번 수정하는 방식.
C. 초기 정보를 제공하고 검증·추가 조회·재계획을 수행하는 Agent.

동일한 모델, 초기 일정, 조건, 변화 이벤트를 사용한다. B와 C는 같은 초기 관측 정보를 받으며 C의 추가 조회는 기록하고 비용에 포함한다. 추가 정보의 효과와 검증 반복의 효과를 구분하기 위해 합성 환경에서는 전체 동일 정보를 제공한 비교도 수행한다.

### 시나리오

비 예보, 일정 지연, 현장 휴무, 선호 변경, 고정 예약 충돌, API 실패, 정보 부족, 충족 불가능한 조건, 유효 대안 1~2개, 오래된 제안 선택, 중복 선택을 포함한다.

합성 데이터는 고정된 시계와 도구 응답으로 재현한다. 실제 연동 테스트는 지원 범위와 최신 응답 형태를 확인하는 데 사용하고 재현 평가 결과와 분리해 보고한다. 여러 번 실행한 결과와 실행 설정을 함께 남긴다.

### 지표

- 제약 충족률: 전체 적용 제약 중 충족이 확인된 비율. 위반과 미확인은 별도로 보고하고 미확인을 통과로 세지 않는다.
- 대응 성공률: 가능한 경우 유효 대안을 제시하고, 불가능한 경우 원인을 올바르게 안내한 시나리오 비율.
- 제안 유효성: 후보별 검증 결과와, 3개 이상 가능한 시나리오에서 구별되는 유효 후보 3개 제공 여부.
- 불필요한 변경: 영향 없는 일정 중 변경한 항목 수와 이유를 보고한다.
- 상태 일관성: 완료·고정 일정 보존, 거절 시 원본 유지, 선택 한 번 반영, 버전 충돌 처리.
- 효율: 응답시간 분포, 도구·LLM 호출 수, 추정 비용, 반복 횟수.
- 설명 품질: 변경 이유·영향·미확인 사항이 실제 검증 결과와 일치하는지 수동 평가한다.

### 필수 통과 기준

자동화된 상태·제약 시나리오에서 사용자 동의 없는 고정 조건 변경, 완료 일정 변경, 거절된 제안 반영, 미확인 정보의 통과 처리, 중복 선택의 중복 반영이 없어야 한다. 실패·대안 부족 시나리오가 정해진 한도 안에서 종료되어야 한다.

Agent가 비교 방식보다 낫다는 주장은 측정 결과가 뒷받침할 때만 한다. 우위가 없으면 실패 유형과 비용 대비 효과를 분석해 개선한다.

## 12. 개발 순서와 산출물

1. 상태·조건·도구 계약과 합성 시나리오를 정의한다.
2. 기존 일정 하나에 대해 변화 → 검증된 대안 3개 → 사용자 선택 → 반영 흐름을 연결한다.
3. 실제 API와 오류 처리를 연동한다.
4. 여행 모드의 주기 확인·알림·중복 억제를 연결한다.
5. 새 일정 생성과 자유 텍스트 입력을 연결한다.
6. 화면에서 원본·대안 비교와 상태 입력을 완성한다.
7. 비교 평가를 실행하고 결과·한계·시연 절차를 문서화한다.

최종 산출물은 실행 가능한 앱, 재현 가능한 시뮬레이션, 테스트·평가 결과, 아키텍처와 의사결정 문서, 실제 API 시연 절차다.

문서 검토 후 구현 계획을 작성한다. 구현 계획에서 파일 구조·기술 스택·구체적인 설정 기본값·단계별 검증 명령을 확정한다.

## 13. 개발 환경 호환성 (추가 합의)

Windows PC와 macOS MacBook에서 같은 프로젝트를 개발·실행할 수 있어야 한다. OS 전용 절대 경로·셸 명령을 앱 코드에 넣지 않고, 공통 의존성 잠금 파일과 실행 명령을 제공한다. 두 운영체제의 설치·테스트·빌드 검증을 완료 기준에 포함한다. 코드와 잠금 파일은 Git으로 이동하고 비밀 키와 가상환경은 장비별로 구성한다. 로컬 여행 데이터의 장비 간 자동 동기화는 이번 합의에 포함하지 않는다.
